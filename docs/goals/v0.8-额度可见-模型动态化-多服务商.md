## 阶段一：WorkBuddy OAuth 落地 + 额度读数（先做）

### G1 完成一次真实 OAuth 登录
**目标**：设置卡 OAuth 区可用真实浏览器完成一次完整登录；token 落 `~/.dsh/codebuddy-plugin-auth.json`；`oauthStatus()` 显示已登录账户信息。
**注意**：用户在 WorkBuddy 客户端和个人中心都能看到额度 → 额度数据必有服务端来源；本阶段登录是后续探测的前提。

### G2 真实 token × 端点矩阵探测（解锁三个未解课题）
**目标**：用真实 token 跑只读探测矩阵（oauth-handshake.md §5 的解锁清单）：
1. token vs `ck_` key 的端点可达差异（accounts / config / dosage-notify / agenttool / chat）。
2. **额度端点搜寻**：WorkBuddy 客户端与个人中心能看到的额度，其背后的 API——从 copilot.tencent.com 与 www.workbuddy.cn 两个域名找 plan / billing / credit 类端点，用 token 授权实测。网页 cookie API 若 token 进不去，诚实标注记入规则文档（可考察 OAuth 登录浏览器态与 plan API 的关系，但不下结论）。
3. refresh 轮换语义（旧 token 复跑观测作废码）。
**红线**：只读、低速率、单账号。本次额度端点探测是**用户明确授权的探测面扩展**（此前 cookie 体系按红线不碰，现在用户主动要求解锁）；新发现全部写入 `docs/rules/quota-signals.md` 或新规则文档。

### G3 额度卡片（聊天页）
**目标**：dsh 聊天页/设置卡直观展示：本轮消耗（credit + token 拆解：prompt/缓存命中/输出）、今日合计、累计、近 N 轮趋势；数据源 `usage-meter.view()`。
**剩余额度**：G2 探到 API 就显示真实值；探不到就做「总额度手填 − 累计已耗」估算档，UI 必须标注"估算"。禁止假装有真实数值。
**低额告警**：dosage-notify 文案非空时卡片警示色 + 文案。
**验收**：卡片数值与 `codebuddy-plugin-usage.json` 最新 entry 一致；不阻塞聊天主链路（零行为变更纪律不变）。

## 阶段二：模型动态化 + 上下文长度组件

### G4 模型列表动态化
**目标**：模型清单默认从 `/v3/config` 自动同步（启动拉取 + 设置卡手动刷新按钮），静态清单降级为离线兜底。
**约束**：同步写 settings.yaml 遵守踩坑 #6 纯净态纪律；拉取失败必须无感回落静态清单，绝不让模型选择器变空。

### G5 上下文长度调节组件
**目标**：设置卡里每个模型可调**上下文长度**（maxInputTokens 覆盖值，含 maxOutputTokens），改动同步 settings.yaml 即时生效。
**数据源**：`/v3/config` 的 maxInputTokens / maxOutputTokens 是每模型实际上限，作为默认值与调节上限。

## 阶段三：多服务商凭据中心（core 多上游的 UI 兑现）

### G6 服务商注册表（key 型，先落地）
**目标**：设置卡可添加多个 OpenAI 兼容上游（名称 + baseURL + key），每个上游一个 `providers/<name>/` 适配器实例，模型统一进选择器。
**已知可接 key 型上游**（用户手上就有额度）：火山引擎 ark（Agent Plan key）、阿里云百炼。
**纪律**：新上游特化代码进 `providers/<name>/`，**core/ 零改动**（verify-core-generic 必须保持绿）。

### G7 本机登录态自动检测（登录型，渐进做）
**目标**：扫描本机已安装 agent 工具的登录态/凭据文件，检测到即在设置卡提示「发现 XX 凭据，一键导入」。
**用户点名的探测清单**（执行时逐个定位安装目录与凭据存储，以本机实际为准）：TRAE、ZCode、豆包桌面端、Qoder、千问办公、Kimi、官方 CodeBuddy CLI，以及其他 agent plan 类工具。
**交互形态**：用户接受"一个一个登录"的渐进接入——今天导入一个、明天导入一个，互不影响；但**不做"一个一个手动配置"**——检测到就该是一键导入。
**红线**：只读检测；导入前逐个用户确认；凭据文件路径与内容不落日志；不碰凭据文件以外的私有数据。

## 全局验收（每阶段完成时自查）

1. 现有 CodeBuddy 链路零行为变更（UA / 错误码 / developer 重写 / 凭据来源不变）。
2. 四项回归全绿：`npm run verify` / `npm run verify:bridge` / `npm run verify:core` + `node scripts/verify-rotation.mjs`。
3. 新凭据（token/key）永不回传浏览器、不进日志（脱敏规则同现有 maskKey）。
4. 新网关事实写入 docs/rules/ 对应文档，STATE.md 追加进展。
5. UI 改动跑浏览器回归（踩坑 #4 / #15 / #16 / #18）。

## 过程指引（仅方向，不锁步骤）

- 顺序建议：阶段一 → 二 → 三。G3 依赖 G2 结论，G5 依赖 G4 数据，其余可并行处自行判断。
- 逆向/探测沿用六课题工作法：假设 → 预注册预测 → 实测 → 写规则文档（证据落 docs/probes/）。
- 遇到需要用户交互的点（浏览器登录、导入确认、手填总额度），明确停下提示，不替用户决定。
- 任何与本文件冲突的旧结论，以新实测为准，并更新规则文档。
